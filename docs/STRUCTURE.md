# Структура проекта

Документ отвечает на вопрос «куда положить новый код», чтобы через полгода
проект не превратился в свалку.

## Дерево

```
src/
  app/                    Next.js: страницы и HTTP-маршруты
    api/
      health/             проверка живости сервиса
  modules/                ВСЯ бизнес-логика
    users/                профиль, связка со Stripe Customer
    auth/                 вход по коду и через Google        (этап 1)
    billing/              Stripe: подписки, платежи, портал  (этап 3)
    api-keys/             ключи, расход, кредиты             (этап 4)
  db/
    schema/               таблицы, разбитые по доменам
    index.ts              подключение к PostgreSQL
  lib/                    инфраструктура без бизнес-логики
    env.ts                валидация переменных окружения
    errors.ts             типизированные ошибки
    logger.ts             JSON-логи
  config/
    constants.ts          все числовые константы приложения
docs/                     документация
drizzle/                  сгенерированные миграции (в git!)
```

## Главное правило — слои

```
app/  →  modules/  →  db/
```

Только слева направо.

| Слой | Что делает | Что ему запрещено |
|---|---|---|
| `app/` | принять запрос, проверить права, вызвать модуль, вернуть ответ | содержать бизнес-логику, обращаться к `db` напрямую |
| `modules/` | бизнес-правила | знать про HTTP, `Request`, cookies |
| `db/` | схема и подключение | содержать запросы |

Почему это важно: как только страница начинает сама ходить в базу, правило
«есть ли у пользователя доступ» размазывается по десяти файлам. Дальше один
разработчик правит его в одном месте, второй — в другом, и никто не может
сказать, как система работает на самом деле.

## Устройство модуля

Одинаковое у всех, чтобы не приходилось разбираться заново:

```
modules/<имя>/
  README.md        зачем нужен, границы ответственности
  types.ts         типы наружу
  repository.ts    запросы к БД — ЕДИНСТВЕННОЕ место с SQL
  service.ts       бизнес-правила
  index.ts         публичный интерфейс
```

Чужой модуль импортируем **только через его `index.ts`**:

```ts
import { getUser } from "@/modules/users";           // да
import { findById } from "@/modules/users/repository"; // нет
```

## Соглашения

- **Импорты** — через алиас `@/`, а не `../../../`.
- **Деньги** — целые числа в центах. Никаких `float`.
- **Даты** — всегда `timestamptz`, в коде UTC. Локальное время только при выводе.
- **Именование в БД** — `snake_case`, в TypeScript — `camelCase`. Сопоставление
  задаётся в схеме явно.
- **Ошибки** — через `AppError` из `lib/errors.ts`. Наружу уходит только `code`
  и `message`, без стек-трейсов.
- **Логи** — через `logger`, не `console.log`. Секретов, кодов из писем и
  API-ключей в логах быть не должно.

## Куда класть новый код

| Задача | Место |
|---|---|
| Новая страница | `app/<путь>/page.tsx` |
| Новый HTTP-эндпоинт | `app/api/<путь>/route.ts` |
| Новое бизнес-правило | `modules/<домен>/service.ts` |
| Новый запрос к БД | `modules/<домен>/repository.ts` |
| Новая таблица | `src/db/schema/<домен>.ts` + миграция |
| Утилита без бизнес-логики | `lib/` |
| Константа или лимит | `config/constants.ts` |
